# Recharts 使用规范

## 文档目标

本文档用于指导项目内使用 Recharts 构建报表图表。
本文档的组件清单以当前依赖版本导出的模块为准。
本文档只定义选型、职责边界、数据约定、布局约定和修改约束。

## 使用原则

Recharts 适合用于需要坐标轴、图例、tooltip、缩放、参考线、多序列对比、组合图等能力的正式图表。

轻量 KPI、头像列表、简单排行条等卡片式报表，应优先使用项目内通用组件：

- `ChartMetricCard`
- `ChartAvatarListCard`
- `ChartBarListCard`

只有当通用报表卡片无法表达图表语义时，才直接使用 Recharts。

## 组件职责边界

Recharts 组件只负责图表渲染，不负责业务数据获取、权限判断、路由读取、store 读写或接口调用。

业务模块应在调用 Recharts 前完成：

- API 数据请求
- 数据清洗
- 空值兜底
- 单位换算
- 数值格式化
- 日期格式化
- 颜色语义映射
- 权限过滤
- 图表类型选择

图表组件内部可以保留与展示强相关的格式化逻辑，但不得写入固定业务数据或业务判断。

## 图表容器组件清单

| 组件 | 用途 | 选型说明 |
| --- | --- | --- |
| `LineChart` | 折线图 | 用于趋势、连续时间序列、变化曲线 |
| `BarChart` | 柱状图或条形图 | 用于分类对比、排行、离散指标比较 |
| `AreaChart` | 面积图 | 用于趋势规模、累计量、区间变化 |
| `PieChart` | 饼图或环形图 | 用于少量分类占比 |
| `RadarChart` | 雷达图 | 用于多个维度的轮廓对比 |
| `RadialBarChart` | 径向柱状图 | 用于环形进度、径向占比、环形分类对比 |
| `ScatterChart` | 散点图 | 用于分布、相关性、异常点分析 |
| `ComposedChart` | 组合图 | 用于混合折线、柱状、面积等多图形对比 |
| `FunnelChart` | 漏斗图 | 用于阶段转化、流程流失 |
| `Treemap` | 矩形树图 | 用于层级数据的面积占比 |
| `Sankey` | 桑基图 | 用于流向、转移、能量或资金路径 |
| `SunburstChart` | 旭日图 | 用于层级结构占比 |

## 容器和布局约定

图表应放入稳定尺寸的容器中，避免渲染时高度为 0 或随内容跳动。

推荐规则：

- 图表区域必须有明确高度。
- 响应式图表优先使用 `ResponsiveContainer`。
- 图表外层布局由业务组件或 shadcn `Card` 负责。
- Recharts 图表组件不要承担页面网格布局职责。
- 同一页面内的同类图表高度应保持一致。
- 图表标题、描述、筛选器、操作按钮应放在图表外层组件中，不要塞入 Recharts SVG 区域。

## 数据建模约定

传入 Recharts 的数据应是稳定、扁平、可序列化的数据结构。

规则：

- 每条数据应有稳定的分类字段或时间字段。
- 多序列图表应使用清晰的 `dataKey` 命名。
- 数值字段必须在传入前处理为 number。
- 缺失值、空字符串、非法数字、NaN、Infinity 必须在传入前处理。
- 时间数据应在模块层统一格式化展示标签，避免不同图表重复格式化。
- 不要把后端原始响应直接传给图表组件。
- 不要在图表组件内部推断接口字段含义。

## 样式约定

图表颜色应遵循项目主题和语义色，不要在业务组件中随意堆叠临时色值。

规则：

- 优先使用 CSS 变量、Tailwind 语义 token 或项目统一颜色映射。
- 同一业务含义在不同图表中应使用一致颜色。
- 上涨、下降、异常、警告等状态应由调用方统一映射。
- 坐标轴、网格、tooltip、legend 的视觉层级应弱于核心数据图形。
- 不要让装饰色压过数据色。
- 不要在多个图表中重复散落硬编码颜色。

## Tooltip 和 Legend 约定

`Tooltip` 用于补充精确值，`Legend` 用于解释多序列含义。

规则：

- 多序列图表通常需要 `Legend`。
- 单序列且标题语义明确的图表可以省略 `Legend`。
- `Tooltip` 显示值应使用业务单位和格式化规则。
- 百分比、金额、时长、次数等单位不能混用。
- Tooltip 文案不得暴露后端字段名。
- Legend 名称应使用面向用户的展示名称，不使用技术字段名。

## 坐标轴约定

坐标轴应服务于读数，不应制造额外视觉噪音。

规则：

- 分类轴标签应简短，过长文本应在数据层或展示层处理。
- 数值轴应按业务单位格式化。
- 金额、百分比、次数、时长应有明确刻度格式。
- 不需要精确读数的小型趋势图可以弱化或隐藏坐标轴。
- 对比图表的轴范围必须避免误导。
- 双轴图表必须清晰区分单位和序列含义。

## 组合图约定

需要同时表达不同图形类型时使用 `ComposedChart`。

规则：

- 组合图必须保证每个序列的业务含义明确。
- 不同单位的序列不得混用同一坐标轴。
- 柱状、折线、面积混合时，应控制视觉优先级。
- 不要为了节省空间把过多指标塞进一个组合图。
- 指标过多时应拆分为多个图表或提供筛选能力。

## 空数据和异常状态

图表组件必须考虑空数据状态。

规则：

- 空数组不应导致运行时异常。
- 数据加载中应由外层组件渲染 loading 或 skeleton。
- 数据为空应由外层组件渲染 empty state。
- 接口异常应由外层组件处理错误状态。
- Recharts 组件内部不负责请求重试或错误提示。

## 可访问性约定

图表不得成为唯一的信息来源。

规则：

- 关键数值应在标题、摘要、tooltip 或辅助文本中可读取。
- 颜色不能作为唯一语义表达。
- 交互图表应保证键盘和屏幕阅读器用户至少能获取核心信息。
- 对业务关键报表，应提供表格、摘要或可读文本作为补充。

## 性能约定

大型数据集需要在进入图表前处理。

规则：

- 不要把超大原始数据直接传给 Recharts。
- 时间序列数据量过大时应抽样、聚合或分页。
- 复杂 formatter、tooltip renderer、label renderer 应避免在每次 render 中创建昂贵计算。
- 图表数据应在模块层或 hook 中完成 memo 化。
- 不要在图表 render 过程中生成随机数据。
- 不要在图表组件内部执行副作用请求。

## 目录和复用约定

模块私有图表放在对应模块目录：

- `src/modules/<module-name>/components/`

跨模块复用且不含业务概念的图表组件可以上提到：

- `src/components/common/charts/`

跨模块复用但带业务语义的图表组件可以放到：

- `src/components/business/`

上提组件前必须确认存在真实复用关系。不要为了“可能复用”提前抽象。

## 导入约定

业务模块应直接从 `recharts` 导入所需组件。

规则：

- 只导入当前图表实际使用的 Recharts 组件。
- 不要创建全量 Recharts 转出口文件。
- 通用报表卡片统一从 `@/components/common/charts` 导入。
- shadcn/ui 卡片、Tabs、按钮等仍从 `@/components/ui/*` 导入。

## 修改约束

大模型或开发者新增、修改 Recharts 图表时必须遵守：

- 不要把业务请求写进图表渲染组件。
- 不要在图表组件中硬编码接口响应结构。
- 不要在图表组件中写死业务数据。
- 不要在多个图表中复制同一套格式化逻辑。
- 不要把简单 KPI 卡片强行改造成 Recharts 图表。
- 不要为单个页面临时新增全局通用组件。
- 不要把图表标题、筛选器、操作按钮放进 SVG 自定义层。
- 不要绕过项目已有 `ChartMetricCard`、`ChartAvatarListCard`、`ChartBarListCard` 重新实现同类卡片。

## 验证要求

新增或修改 Recharts 图表后至少执行：

```bash
npm run typecheck
npm run lint
```
